# 镜像原生能力驱动调优

SGLang 与 vLLM 使用同一条证据驱动流程，但保留各自的原生参数、默认值和运行时核验方式。不会因为引擎名称或模型名称，就将某项功能固定判定为支持或不支持；也不会将 SGLang 的 DP Attention、DSpark 强行翻译成 vLLM 的功能。

## 新计划的流程

1. **读取配置、模型、GPU 和固定镜像。** 保留既有 CUDA、镜像入口与必需启动参数检查。在实际镜像中读取帮助文本，以及已安装的原生参数解析器：记录参数名、别名、类型、公开默认值、枚举和相关源码片段。vLLM 另尝试提取 `SpeculativeConfig` 的嵌套字段。提取失败记录未知及原因，不猜测版本兼容性。
2. **智能调优请求能力顾问。** 将镜像证据、模型元数据、GPU 和用户限制交给 LLM。顾问可以请求补读已有证据 ID，建议功能维度、原生取值、组合对照、优先级、性能假设与待确认问题。原始业务请求和认证信息不作为能力分析上下文。
3. **生成原生功能对照。** 校验建议的参数结构、公开枚举、资源约束和接入契约；显式 `engine_options` 与 `search.backends` 优先。保留基线，并在候选预算内生成单项和组合对照。TP/DP/PP 等建议映射到已经生成的合法拓扑候选，不是直接修改某个候选的卡数；例如 `tensor_parallel_size: 8` 只匹配原规划器已经确认合法的 8 路 TP 候选，不能把单卡候选改成 TP=8。拓扑和功能组合会在匹配到的合法分配上生成，没有匹配或违反约束时记录拒绝原因。已有候选推荐阶段继续从合法目录选点，不能添加任意 shell 参数。
4. **执行原生解析预检。** 在固定镜像中运行原生解析器，不挂载权重、不启动推理服务，禁用容器网络。先尝试不暴露 GPU；只有实际报错指向设备识别（例如 `Failed to infer device type`）时，才使用配置或合法候选中已经选定的 GPU 上下文重试，不伪造设备类型，也不启动推理。首试与重试共享 180 秒解析预算，超时尽力清理本次探测容器。参数解析明确拒绝的候选不进入正式执行；解析器初始化、设备识别和其他运行环境异常保留为未知，不等价于候选不兼容。智能调优基线若被明确拒绝，则停止生成有效计划并要求检查报告。
5. **开始搜索后实测。** 点击“开始搜索”才加载权重、运行候选和业务回放；Adaptive 仍先测基线，再根据实测调用反馈顾问。模型/GPU 适配、服务启动、实际配置回读、吞吐和时延只能在此阶段确认。

AUTO 使用相同的结构化镜像探测、原生功能对照和解析预检，但不调用能力顾问、候选顾问或反馈顾问。智能模式顾问不可用或响应非法时，保留失败原因，降级到镜像证据支持的规则选点。原始输入、输出上限、采样与思考等业务条件不成为原生功能顾问可修改的调优变量。

## 自动读取模型权重与容量筛选

每次生成 AUTO 或智能调优计划，直接使用 `configs/experiment.json` 已有的 `model_path`，无需手工填写模型参数量或另外指定权重路径。扫描只读取本机的配置、分片索引与 safetensors 张量头，不读取张量数据、不导入模型代码、不占用 GPU，也不修改模型文件。

- 优先按 `model.safetensors.index.json` 选择实际分片，避免把额外权重副本、adapter 或无关文件重复相加；支持标准单文件与完整标准编号分片。检查张量形状、dtype、偏移及文件完整性，记录每个头的哈希。
- 汇总存储张量元素数、dtype、权重数据字节数及文件大小。未量化浮点检查点的元素数用于显示规模，但不冒充去重逻辑参数量；MoE 不使用激活参数量替代总权重。量化打包张量不能直接还原逻辑参数量，保持未知。
- 对证据完整的未量化浮点检查点计算保守常驻权重下界：FP32 允许按半精度加载，省略可能共享的输出头和可选草稿层。量化、未知 dtype、混合整数存储、多模态部分加载、自定义 `profile_env` 等情况不做硬淘汰。`.bin` 不反序列化，只记录文件/索引大小；GGUF 等未接入格式保持未知。
- 按每个实例可分片的 GPU 显存判断，而非所有实例显存相加。例如 8 卡 8 实例每个模型副本只有一张卡；Dense DP 不切分权重，按 TP × PP 的容量计算；MoE 为避免误杀可被 EP 救活的候选，乐观使用整个实例的容量。只淘汰连这个乐观容量都无法容纳权重下界的基础候选，后续原生功能变体只能基于保留拓扑生成。
- 通过容量检查只表示没有证明不可能，不代表能启动。KV cache、激活、CUDA graph、kernel 工作区、不均匀分片等仍需实测；假设常驻 GPU、没有 CPU/磁盘卸载或运行期量化。无法证明时保留候选并标注未知，不根据模型名称猜测。

智能调优把紧凑的 `context.model_weights` 和 `context.weight_capacity` 交给已有能力分析顾问，包含 dtype、规模、量化、容量淘汰和未知项；不发送权重文件内容，也不给顾问文件访问或执行权限，不新增一次独立 LLM 调用。AUTO 使用相同读取和确定性筛选，但仍完全不调用 LLM。全部基础候选被容量淘汰时停止生成计划，先落盘权重报告和淘汰依据，不浪费顾问或启动预算。

在“镜像原生能力 → 模型权重自动识别”查看规模、容量筛选和未知项；计数为生成原生参数变体前的基础候选，不是最终运行次数。`model-weights.json` 保存详细扫描证据，`weight-capacity.json` 保存逐基础候选的每副本容量与排除理由；计划冻结两个报告的哈希，执行/恢复前校验。旧计划不回填、不重新筛选，需重新生成计划才启用。

## 两个引擎的接入边界

- **SGLang：** 原生投机算法、草稿 token 数、DSpark block size、投机步数/EAGLE top-k、EP size、MoE runner 和 A2A。Attention DP 拓扑按镜像公开的 `--attn-dp-size` 或旧开关生成，并同步实际命令与回读预期；新结构化镜像不再靠固定 DSPARK block size 生成投机候选。
- **vLLM：** Expert Parallel、All2All backend、MoE backend，以及原生 `speculative_config`。嵌套建议必须来自镜像实际字段，只接受可核验的标量类型和已知枚举；不能借投机配置修改模型、路径、tokenizer、量化或缓存条件。
- **既有拓扑映射：** vLLM 的 `tensor_parallel_size`、`data_parallel_size`、`pipeline_parallel_size`；SGLang 镜像公开的 TP/DP/PP 参数、Attention DP 大小和开关。目录中的 `existing_planner` 表示建议通过合法拓扑选择生效，不作为额外静态参数注入启动命令，也不会绕开模型头数、层数、物理 GPU 和显式配置限制。
- **接入契约不是兼容性白名单：** 参数是否存在、支持哪些公开值来自镜像；参数能否被自动修改，还要求 LLMPerf 已有安全的启动与实际参数回读适配。未接入的原生参数仍保存在证据目录，标注为“已发现、未接入”，不宣称引擎不支持。新增任意原生 CLI 参数不会自动获得执行权限。
- **解析器也有边界：** 预检只验证提交给解析器的功能与拓扑参数，不能代替完整模型加载、GPU kernel、模型正确性或吞吐测试。设备上下文重试仍失败、无选定 GPU 或遇到非设备异常时保持未知，并保留每次上下文与错误。

## 配额与状态

能力分析最多 3 个逻辑轮次，各轮共享最多 2000 秒；`advisor.timeout_seconds` 更短时按更短值执行。与候选推荐、运行期 `search.adaptive.max_advisor_calls` 的反馈额度独立，不会减少反馈额度。每轮沿用错峰请求策略；逻辑轮次不等于实际 HTTP 请求次数，界面和产物分别记录实际请求数和胜出序号。

沿用 `advisor.thinking` 和 `advisor.reasoning_effort`。如需最大思考，使用 `thinking: true`、`reasoning_effort: "max"`；是否实际生效以顾问服务为准。能力分析输出预算优先级为 `task_max_tokens.capabilities` → `task_max_tokens.candidates` → 8192，无需新增配置字段也可以使用此阶段。

必须区分以下状态：

| 状态 | 含义 |
| --- | --- |
| 已发现 | 镜像帮助或结构化解析器中存在该参数 |
| 已发现、未接入 | 镜像公开该参数，但 LLMPerf 尚无完整自动执行/核验契约 |
| 顾问建议 | 有证据引用的功能或实验提议，不是支持性结论 |
| `preflight_passed` | 原生参数解析通过，仍待实测 |
| `parser_rejected` | 原生解析器明确拒绝本次参数 |
| `unknown` | 探测或解析信息不充分，不能据此认定不支持 |
| 预检整体 `partial` | 一部分参数用例可验证，一部分仍未知 |
| 预检整体 `completed` | 每个用例都得到了明确的解析通过或拒绝结果，不是整组实测通过 |
| Trial 有效 | 正式执行通过现有运行、实际参数回读和业务响应校验 |

如果 256 个候选全部是 `unknown`，整体必须显示未知，不能仅因探测脚本结束就标为 `completed`。页面也兼容旧报告：即使旧 JSON 写的是 `completed`，仍按逐候选全未知结果显示“未完成验证（未知）”和具体原因，不回写冻结的报告文件。

## 从哪里查看

选择新生成的 run，在“运行概览 → 镜像原生能力”查看分析状态、逻辑轮次/实际 HTTP 次数、建议、假设、待确认问题、建议校验拒绝和用户限制过滤。“顾问建议落地”显示每项建议匹配到的最终候选 ID；未进入候选池不等于运行失败，已进入候选池也不等于已经运行。“原生解析预检诊断”显示设备上下文、重试记录和汇总未知原因。候选表按引擎分列展示规划值与解析预检；规划值不冒充实际生效值。

结果目录保存：

- `engine-capabilities.json`：镜像身份、结构化参数目录和源码证据。
- `capability-analysis.json`：智能模式的逐轮输入、响应、证据请求、建议、拒绝原因和调用审计；AUTO 不生成此文件。
- `native-preflight-input.json`：本次解析预检的参数用例，不含模型权重或业务请求。
- `native-preflight.json`：预检范围、聚合状态、逐候选结果、设备上下文、各次尝试和汇总未知原因。
- `plan.json`：冻结的能力快照、候选、分析摘要与证据文件哈希；`native_generation` 记录拓扑提升和组合约束拒绝，`capability_proposal_outcomes` 记录建议与最终候选的对应关系。

能力目录、智能模式分析、预检结果及新增的权重扫描与容量筛选报告的哈希在执行/恢复时校验，修改报告后不能当作原计划继续运行。真正运行后的实际配置应查看 Trial 的 `server.info.json`、`server.evidence.json` 和 `server.command.sh`，而非仅看顾问建议。

更新后需重启 Web 服务并刷新页面，重新生成计划才会进入新阶段。旧计划继续使用冻结候选；严格 Resume 或“接受当前代码 Resume”都不会自动重新分析镜像或扩展候选。
